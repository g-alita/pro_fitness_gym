# AWS Lambda backend

- Package the project root so the deployment includes `backend/`, `frontend/`, `package.json`, and `node_modules/`.
- Use a supported Node.js Lambda runtime and set the handler to `backend/lambda.handler`.
- Expose the function through an API Gateway HTTP API or Lambda Function URL. The Express adapter supports API Gateway events; the app serves the frontend as well as its API routes.
- Set `MONGO_URI`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `GOOGLE_CLIENT_ID`, `RESEND_API_KEY`, `EMAIL_FROM`, `CONTACT_EMAIL`, the WhatsApp variables below, a stable `AUTH_SESSION_SECRET`, and a separate stable `PHONE_OTP_SECRET` in Lambda environment variables. `MONGO_URI` must allow connections from the deployed function.
- Email sign-in code requests are checked against MongoDB's `user mail` or admin email allowlist before Supabase sends a code. The code is verified by Supabase, then the allowlist is checked again before the app session is issued. Unlisted emails cannot obtain an app session. Other existing sign-in methods also retain their MongoDB allowlist checks.
- Configure a Google OAuth 2.0 Web application client in Google Cloud. Add each website origin (for example `https://your-site.example`) under **Authorized JavaScript origins**, and set its client ID as `GOOGLE_CLIENT_ID` in Lambda. No Google redirect URI or Supabase Google provider setup is needed for this direct Google Identity Services flow. The client ID is public; never put the Google client secret in the frontend or Lambda.
- Both user and admin Google buttons use Google Identity Services directly. The browser sends the Google ID token to Lambda, where `google-auth-library` verifies the token against `GOOGLE_CLIENT_ID`; the backend then checks the corresponding MongoDB allowlist before issuing the app session. Admin authorization is based on MongoDB's `admin mail` or enabled `admin_allowlist` entries; user authorization is based on MongoDB's `user mail` entries. Environment-variable email allowlists do not grant login access.
- Supabase is still used for email OTP only. In Supabase, enable the Email provider, set the email OTP length to 6, and configure its email template to show the numeric code using `{{ .Token }}`. Configure Supabase Auth email delivery for production. The backend requests email OTP only after the email passes the MongoDB allowlist check.
- Phone sign-in for both users and admins sends a six-digit OTP through the WhatsApp Cloud API. Configure `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_GRAPH_API_VERSION` (for example `v27.0`), `WHATSAPP_OTP_TEMPLATE_NAME`, and `WHATSAPP_OTP_TEMPLATE_LANGUAGE`. Keep the access token only in Lambda environment variables; it is never sent to the browser or written to logs.
- In Meta WhatsApp Manager, create and get approval for an **Authentication** message template that accepts the OTP in its body and has the URL/copy-code button at index `0`; set the exact approved template name and language in Lambda. The website requires the visitor to enter the delivered six-digit code, so configure an OTP copy-code flow rather than a zero-tap/one-tap flow that requires a native-app handshake. Make sure recipients have opted in to receive WhatsApp messages from the business.
- Before sending a code, the backend checks `profitnessgym.user number` for users or the enabled `profitnessgym.admin_allowlist` entries for admins. It checks the allowlist again before issuing a session. Codes are HMAC-hashed in the `phone_login_otps` collection, expire after 10 minutes, are consumed after successful verification, and have a five-attempt limit plus a one-minute resend cooldown. The collection has a MongoDB TTL index; Lambda's per-process IP limiter is supplementary, so configure API Gateway throttling as well.
- Set `APP_BASE_URL` to the public site URL for password setup/reset links. Email sign-in no longer uses SMTP; SMTP remains required for password setup/reset emails.
- Use a supported Node.js Lambda runtime with built-in `fetch` and `AbortSignal.timeout` (Node.js 20 or later). Lambda rate limits are process-local; configure API Gateway throttling for additional shared request throttling.
- If hosting the frontend separately, set `window.PRO_FITNESS_API_BASE_URL` in `frontend/api-config.js` to the API Gateway base URL (include the stage if the URL has one), and set `FRONTEND_ORIGIN` to the frontend origin in Lambda. This enables credentialed CORS and secure cross-site auth cookies. Leave the API base empty and omit `FRONTEND_ORIGIN` when the site and API share an origin.
